## 一、方案 A 新引入的问题（专审）

### 🔴 P0-1: merge_subs 方案 A 自反馈环

**位置**：`merge_subs.py:284-286`
**问题类型**：逻辑漏洞 — 自引用
**具体描述**：
```python
name_index = {n.get("name"): n for n in nodes if n.get("name")}
for nd in load_clash_yaml(os.path.join(base, "s-clash.yaml")):
    if isinstance(nd, dict) and nd.get("name") and nd["name"] not in name_index:
        name_index[nd["name"]] = nd
```
`merge_subs` 把上一轮自己产出的 `s-clash.yaml` 的 proxies 加入 `name_index`，作为旧格式 `verified.json` 的降级匹配源。但 `s-clash.yaml` 里已包含**上一轮已验证通过的节点**（带 `✅` 前缀）。当旧格式 `verified.json` 降级时，会匹配到 `s-clash.yaml` 里带 `✅` 前缀的节点名，导致：
- 已验证节点被**重复降级匹配**（虽然去重键 `(type,server,port)` 会去重，但 proxy 配置可能被覆盖为旧版）
- 形成自反馈：s-clash.yaml 里的节点 → name_index → 下一轮 matched proxy → 写回 s-verified → 再进 s-clash

**影响**：当前新格式已验证的 verified.json 不走降级，所以此问题当前不触发。但一旦容器跑出新格式（带 proxy），降级路径不再被使用，自反馈环实际不会执行。**属于"静默炸弹"——若未来某次 verified.json 格式回退，会触发。**

**建议方向**：为 `name_index` 增加来源标记，排除带 `✅` 前缀的节点；或移除 s-clash.yaml 降级源（仅保留当前源 txt/yaml 的新节点，已验证节点应直接来自 verified.json）。

### 🔴 P0-2: CI 的 `git add s-verified.txt` 可能触发 pathspec 不匹配

**位置**：`.github/workflows/update-subs.yml:73`
**问题类型**：流程问题 — 文件不存在
**具体描述**：
```yaml
git add s-clash.yaml s-clash.txt s-verified.yaml s-verified.txt
```
`merge_subs.py` 方案 A 的 `write_verified` 只产出 `s-verified.yaml`，**不产出 `s-verified.txt`**。`s-verified.txt` 是旧版 `tag_verified.py` 的产物（已删除）。如果 `s-verified.txt` 在仓库中已被删除或不存在，`git add` 会报 `pathspec 's-verified.txt' did not match any files`。

**影响**：若 `s-verified.txt` 已被 git 跟踪且上次被删除，`git add` 对已删除的跟踪文件会报错 → CI 失败。验证：本机 `ls` 显示 `s-verified.txt` 存在（旧版残余），但 CI 每次全新 checkout 后可能没有。

**建议方向**：从 `git add` 列表移除 `s-verified.txt`，或确认该文件是否仍需被跟踪。

## 二、高优先级问题（P0）

### 🔴 P0-3: run_local `-X ours` 合并策略可能破坏 CI 产物

**位置**：`verify_cn/run_local.py:452`
**问题类型**：逻辑漏洞 — 并发冲突策略错误
**具体描述**：
```python
mc, mo = _git(["merge", "--no-edit", "-X", "ours", "FETCH_HEAD"], check=False)
```
`-X ours` 策略在本地 `verified.json` 与远端冲突时，**无脑取本地版本**。但容器（run_local）和 CI（update-subs.yml）都可能写入 `s-clash.yaml` / `s-verified.yaml` 等文件。当容器 push 时若 CI 恰好在同一秒也提交了 `s-verified.yaml` 更新，`-X ours` 会静默丢弃 CI 的改动。

**影响**：概率极低（同一秒并发），但一旦触发，会导致 `s-verified.yaml` 回退到旧版本，且 CI 不会重新拉取（因为 `git diff --cached --quiet` 判断无变化），造成验证通过节点丢失。

**建议方向**：`-X theirs` 更安全（取远端版本，本地 verified.json 整体重写，取远端无影响），或改为 `fetch + rebase` 而非 `merge -X ours`。当前实际因容器 push 后 CI 通过 schedule 触发而非 push 触发，并发窗口极窄，可暂不修但应加注释说明风险。

### 🔴 P0-4: CI 不监听 verified.json push，方案 A 的"自动触发"失效

**位置**：`.github/workflows/update-subs.yml:10-12`
**问题类型**：流程问题 — 触发断层
**具体描述**：
```yaml
on:
  schedule:
    - cron: '0 */1 * * *'
```
`update-subs.yml` 只靠每小时 schedule 触发，**没有 `on: push: paths: verify_cn/verified.json` 触发器**。容器每次（15分钟）推 verified.json 后，CI 最长等 1 小时才重新合并产出 s-verified.yaml。`run_local.py:442` 的注释说"GitHub 端 verify-tag 将自动打标产出 s-verified.yaml"是旧版描述，方案 A 已删除 verify-tag，但未更新触发方式。

**影响**：s-verified.yaml 更新延迟 0-60 分钟（平均 30 分钟延迟），而不是预期的"push 后几分钟内"。

**建议方向**：在 `update-subs.yml` 增加 `on: push: paths: ['verify_cn/verified.json']` 触发器，让容器 push verified.json 后立即触发 CI 重新合并。

### 🔴 P0-5: merge_subs 的 `load_verified_proxies` 降级路径存在过时数据风险

**位置**：`merge_subs.py:83-88`
**问题类型**：逻辑漏洞 — 数据时效性
**具体描述**：
当旧格式 `verified.json`（无 proxy 字段）降级时，用 `name_index[name]` 取 proxy。而 `name_index` 包含的 `s-clash.yaml` 节点是**上一小时**的产物，其中的 proxy 配置（server/port/uuid/password 等）可能已被上游更新（如端口变更、密码更换）。降级匹配拿到的可能是**过时的节点配置**。

**影响**：当前已验证的 json 已带 proxy（方案 A 新格式），降级路径不会触发。但若某次验证器故障导致新 json 无 proxy 字段，降级路径会产出过时配置的 s-verified.yaml。

**建议方向**：保持现状（降级只是过渡兼容，新格式一跑即退出），但加显式 `warn` 日志提示"降级模式：使用 name_index 匹配，可能为过时配置"。

## 三、高优先级问题（P1）

### 🟠 P1-1: `_mihomo_accepts` 超时误判坏节点

**位置**：`verify_cn/run_local.py:155`
**问题类型**：逻辑漏洞 — 边界条件
**具体描述**：
```python
r = subprocess.run([mihomo_bin, "-t", "-d", wd, "-f", cp],
                   capture_output=True, text=True, timeout=30)
```
`timeout=30` 秒的超时被 `except Exception` 捕获（line 158）并返回 False，导致二分法把整批正常节点判定为"坏节点"并递归移除。虽然 30 秒对 mihomo -t 足够，但极端情况（容器 IO 压力、大配置 400+ 节点）可能超时。

**影响**：极端情况下二分隔离可能误杀正常节点，导致这批节点不被验证。

**建议方向**：加长超时到 60 秒；或在 `except` 分支增加 `logging.warning` 记录超时信息，便于排查误判。

### 🟠 P1-2: update_nodes `_udp_resolve_a` 串联多个 DNS 超时

**位置**：`update_nodes.py:265-307`
**问题类型**：逻辑漏洞 — 超时累积
**具体描述**：
`dns_resolve` 对 4 个 DNS 服务器逐个调 `_udp_resolve_a`，每个设 `timeout=4` 秒。若 4 个服务器都超时，总耗时 16 秒，超过主流程的 TCP 超时窗口（5-8s）。但 `dns_resolve` 外层有线程 `join(timeout)` 保护（line 337），所以实际不会无限阻塞，但大量串联超时会拖慢整体处理速度。

**影响**：节点量大时（800+），DNS 解析阶段可能累积数分钟的超时等待，逼近 CI 的 20 分钟上限。

**建议方向**：改为并发查询 4 个 DNS 服务器（`ThreadPoolExecutor`），取最快响应；或减少服务器数量到 2 个（阿里+腾讯 DNS 对国内已足够）。

### 🟠 P1-3: `fetch_tuijian.py` 产出完全未被消费

**位置**：`fetch_tuijian.py:14-15` + `merge_subs.py:51`
**问题类型**：流程问题 — 数据流断层
**具体描述**：
`fetch_tuijian.py` 产出 `latest_tuijian.txt` 和 `history_tuijian.txt`，但 `merge_subs.py` 的 `TXT_SOURCES` 里只有 `s.txt/s1.txt/s2.txt`，**没有 `latest_tuijian.txt`**。这个脚本的产物完全未被下游消费，只是占用了 CI 运行时间（约 5-10 秒/轮）。

**影响**：无数据丢失，但浪费 CI 资源；且 `history_tuijian.txt` 无限增长（append 永不清理），可能膨胀到 KB 级。

**建议方向**：确认 `fetch_tuijian.py` 是否仍需保留。若否，从 CI 工作流移除 `continue-on-error: true` 的 step；若需保留，把 `latest_tuijian.txt` 加入 `TXT_SOURCES` 或改名为 `s.txt`。

### 🟠 P1-4: 容器 run_loop.sh 首轮延迟 15 分钟

**位置**：`verify_cn/set_schedule.sh:56` / `verify_cn/cloud_init.sh:128`
**问题类型**：流程问题 — 启动延迟
**具体描述**：
```bash
while true; do
  sleep 900
  ...
done
```
`sleep 900` 写在循环体最前，每次启动后先等 15 分钟才跑第一次验证。`cloud_init.sh` 末尾会立即跑一次，但之后若容器重启或 `set_schedule.sh` 重跑，都会先等 15 分钟才产出第一份 verified.json。

**影响**：容器重启后最长 15 分钟无验证数据，s-verified.yaml 更新停滞。

**建议方向**：改为先跑一次再 sleep：
```bash
while true; do
  ...  # 验证逻辑放前面
  sleep 900
done
```

### 🟠 P1-5: update_nodes 的 `is_cn_ip` 线性扫描 1 万条 CIDR

**位置**：`update_nodes.py:233-235`
**问题类型**：性能瓶颈
**具体描述**：
```python
for net in CN_RANGES:
    if addr.version == net.version and addr in net:
        return True
```
CN_RANGES 约 1 万条 CIDR，每次 `is_cn_ip` 线性扫描。每节点在 `dns_resolve`（过滤 CN IP）和 `test_node_final`（判定 CN IP）中各调一次，节点量 800+ 时就是 800*2*10000 ≈ 1600 万次比较。虽发包量级下不显著，但纯 CPU 密集操作累计可到数秒。

**影响**：节点量大时，CPU 时间被线性扫描占用，但通常不成为瓶颈（TCP 超时才是）。

**建议方向**：用 `ipaddress` 按版本分桶 + 排序的 CIDR 列表做二分查找（`ipaddress.summarize_address_range` 或 `bisect`）；或引入 `cidr-tree` 库。优先级低。

## 四、中优先级问题（P2）

### 🟡 P2-1: merge_subs 步骤编号重复

**位置**：`merge_subs.py:296` 和 `merge_subs.py:306`
**问题类型**：可维护性
**具体描述**：
```python
    # 4) 去重                    ← line 296
    ...
    # 4) name 唯一化（兜底...）   ← line 306
```
两个连续步骤都标为 `# 4)`，第二个应该是 `# 5)`。注释编号错误反映代码维护时的疏忽，容易让后续维护者误以为"去重"被跳过了（因为看到两个 4）。

**影响**：无运行影响，但降低可读性。

**建议方向**：改 line 306 为 `# 5)`，后续步骤编号顺延。

### 🟡 P2-2: `run_local.py` 注释提到已删除的 verify-tag

**位置**：`verify_cn/run_local.py:21-22`、`442`
**问题类型**：文档/注释过时
**具体描述**：
```python
# 6. （可选）git add/commit/push —— push 后自动触发 GitHub 端 verify-tag.yml
#    （监听 verify_cn/verified.json）产出 s-verified.yaml。
```
```python
print("[push] 推送成功；GitHub 端 verify-tag 将自动打标产出 s-verified.yaml。")
```
方案 A 已删除 `verify-tag.yml`，但注释和提示信息仍引用它。会误导阅读者认为还有 verify-tag 在运行。

**建议方向**：更新为"push 后自动触发 update-subs.yml（监听 verified.json）产出 s-verified.yaml"。

### 🟡 P2-3: `update_nodes.py` 的 `_resolve_connect` 在 `probe_proxy_handshake` 中调用但无缓存

**位置**：`update_nodes.py:248-264`、`453-476`
**问题类型**：逻辑漏洞 — 重复解析
**具体描述**：
`probe_proxy_handshake` 内部调 `_resolve_connect(ip)`（line 473），但 `ip` 已经是 IP 地址（不是域名），所以 `_resolve_connect` 的 `is_ip` 分支直接返回，不经过 DNS 缓存。但如果 `ip` 是域名（某些节点 server 字段是域名），`_resolve_connect` 会委托 `dns_resolve`（带 lru_cache）。但 `_resolve_connect` 本身没有 `lru_cache`，相同域名在不同节点间重复解析。

**影响**：域名型节点重复 DNS 解析，每次走 `_udp_resolve_a` 或系统解析器，增加延迟。

**建议方向**：给 `_resolve_connect` 加 `@lru_cache` 或让 `dns_resolve` 的缓存覆盖更广。

### 🟡 P2-4: `fetch.py` 的 `except:` 仍存在

**位置**：`fetch.py:103`、`fetch.py:163`、`fetch.py:213`
**问题类型**：异常处理 — 过宽
**具体描述**：
```python
except:
    continue
```
裸 `except:` 吞掉 `KeyboardInterrupt`/`SystemExit`，在 CI 环境中无法用 `Ctrl+C` 中断，且 `SystemExit` 不会被传递。

**影响**：CI 调试困难，但生产无碍（CI 超时后会被强制取消）。

**建议方向**：改为 `except Exception:`。

### 🟡 P2-5: `node_parse.py` 的 `struct_to_uri` SSR 字段丢失

**位置**：`node_parse.py:429-446`
**问题类型**：逻辑漏洞 — 数据保真度
**具体描述**：
SSR 输出仅 `cipher:password@host:port`（protocol/obfs 等放在 head 中正确），但输出时 `node.get("protocol", "origin")` 和 `node.get("obfs", "plain")` 的默认值可能在 `_parse_ssr` 中未被设置时产生错误默认。实际 `_parse_ssr` 已设置 `protocol` 和 `obfs`（line 231/233），所以当前走此路径时正确。但 `node` 的 `security_scheme` 为 `None`（line 251），`struct_to_uri` 不输出 security 参数，回环后 `_parse_ssr` 的 `security_scheme` 重建为 `None`，不影响功能。

**影响**：SSR 回环解析保真度低，但 SSR 节点已逐渐退出主流，影响小。

**建议方向**：在 `struct_to_uri` 的 SSR 分支输出 `remarks` 时使用原始 name 而非 `_b64(name)`（`_b64` 编码后 v2rayN 可能无法正确显示中文名）。

### 🟡 P2-6: 本机 `run_local.bat` / `setup_schedule.ps1` 无 mihomo 二进制

**位置**：仓库根目录（未读但旧报告提及）
**问题类型**：废弃代码
**具体描述**：本机没有 mihomo 二进制，但 `run_local.bat` 和 `setup_schedule.ps1` 仍存在，执行会静默失败。

**建议方向**：删除或添加 `# DEPRECATED` 标注，或在本机放置 mihomo 二进制前阻止运行。

## 五、低优先级问题（P3）

### 🟢 P3-1: 统一日志格式

**位置**：`fetch.py`（用 `print`）、`run_local.py`（用 `print`）、`update_nodes.py`（用 `logging`）
**问题类型**：可维护性
**具体描述**：项目内日志风格不统一，`fetch.py` 和 `run_local.py` 使用 `print()`，`update_nodes.py` 使用 `logging`。CI 日志中 `print` 输出和 `logging` 输出的时间戳格式不同，排查问题时不连贯。

**建议方向**：统一到 `logging`，`fetch.py` 和 `run_local.py` 使用与 `update_nodes.py` 相同的 `logging.Formatter`。

### 🟢 P3-2: `update_nodes.py` 未使用导入

**位置**：`update_nodes.py:8` (`import binascii`)、`update_nodes.py:14` (`from urllib.parse import urlparse`)
**问题类型**：代码整洁
**具体描述**：`binascii` 和 `urlparse` 被导入但未使用。`urlparse` 在旧版解析逻辑中用，重构后已移除。

**影响**：无，但触发 lint 告警。

**建议方向**：删除未使用的 import。

### 🟢 P3-3: `node_parse.py` 的 `b64decode` 吞异常

**位置**：`node_parse.py:19-26`
**问题类型**：异常处理
**具体描述**：
```python
except Exception:
    return ""
```
`b64decode` 在所有异常时返回空字符串，调用方无法区分"解码失败"和"输入为空"。但当前调用方（`_parse_vmess`、`_parse_ssr` 等）在得到空字符串后都会返回 `None`，所以不影响逻辑。

**建议方向**：保持现状（调用方已正确处理空返回值），或添加 `LOG.debug` 记录异常类型。

### 🟢 P3-4: `fetch_tuijian.py` 的 `datetime.utcnow()` 已废弃

**位置**：`fetch_tuijian.py:72`
**问题类型**：API 兼容性
**具体描述**：Python 3.12+ 中 `datetime.utcnow()` 废弃，3.13 会告警。

**建议方向**：改为 `datetime.now(timezone.utc)`。

### 🟢 P3-5: `requirements.txt` 缺失

**位置**：项目根目录
**问题类型**：环境可复现性
**具体描述**：CI 工作流中硬编码 `pip install requests pyyaml beautifulsoup4 pytest`，无版本锁定。上游依赖更新可能引入兼容性问题。

**建议方向**：创建 `requirements.txt`，锁定当前已知兼容的版本。
